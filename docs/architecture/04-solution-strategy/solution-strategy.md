# 4. Solution Strategy

This chapter describes the fundamental architectural decisions and solution strategies that shape the architecture of
Rationenplaner.

## 4.1. Architectural Decisions and Principles

The following table summarises the fundamental architectural decisions and principles that guide the implementation of
Rationenplaner.

| Principle / Decision                   | Solution Strategy                                                                         | Rationale                                                                                                                                                                                                                                                                                                                                                  |
|----------------------------------------|-------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Client-side first                      | Static, client-side web application                                                       | No backend infrastructure is required to operate the application. The application can be hosted as static files.                                                                                                                                                                                                                                           |
| Separation of concerns                 | Clear separation between user interface, domain logic, algorithms, and data persistence   | Keeps the architecture maintainable and testable by reducing coupling between different responsibilities.                                                                                                                                                                                                                                                  |
| Technology choices                     | React, Tailwind CSS, DaisyUI, Base UI, and Kotlin compiled to WebAssembly (WASM)          | React provides the foundation for the user interface, Tailwind CSS and the UI libraries provide reusable styling and components, while Kotlin/WASM enables computational algorithms to run in the browser. <!-- TODO link to ADR why we chose those technologies -->                                                                                       |
| Storage and Computation independence   | Abstracted storage and computation layer                                                  | Application logic is decoupled from the underlying storage implementation, allowing a transition to server-based storage in the future if necessary. Likewise we decouple algorithm execution environment, allowing calculations to be moved from the client to a server in the future if necessary (e.g. for users with limited computational resources). |
| Client-side persistence                | Persists application data in Browser Storage                                                    | Enables data persistence without requiring backend infrastructure and supports the client-side-first architecture.                                                                                                                                                                                                                                         |
| Explicit data and component versioning | Independent version identifiers for feed components, feed recommendations, and algorithms | Allows individual aspects of the application to evolve independently while maintaining compatibility with existing data. Versioning also provides the foundation for future migrations and notifications to users when relevant changes occur.                                                                                                             |

Data migrations themselves are explicitly out of scope for the current implementation. However, the versioning strategy
establishes the necessary foundation for introducing migrations in the future.
